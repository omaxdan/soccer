# Database V2 — Requirements and Migration Risk Assessment

**Derived only from Phase 1 findings. No schema is proposed here — this document states what V2 must satisfy, not how.**

Covers Phase 1 objectives 7 (Current Problems) and 8 (Migration Risk Assessment) alongside the requirements themselves.

---

## Part A — Current problems V2 must solve

### A1. Technical debt

| # | Problem | Evidence |
|---|---|---|
| TD-1 | **Same quantity stored in up to 7 tables with nothing reconciling them.** Readiness ×7, confidence ×8, strength ×7, squad depth ×7, versatility ×8, formations ×5. | Doc 01 §5.1 |
| TD-2 | **Two independent, competing match predictions ship on the same page.** `match_intelligence.win_probability_*` vs `match_performance_comparison.home_win_probability`/etc. | Doc 03 §4.3 |
| TD-3 | **Inputs and outputs share rows.** `match_intelligence` = 28 copied inputs + 14 outputs; only outputs are frozen after kickoff, so historical rows become internally inconsistent. | Doc 01 §5.2 |
| TD-4 | **31 match-scoped tables where one module-result structure belongs.** Two of them (`match_impact_advantage`, `versatility_advantage`) are structurally identical and differ only in subject. `formation_analysis` and `formation_options` are the same fact in two pivots. | Doc 01 §5.3 |
| TD-5 | **Naming is inconsistent across the schema.** `defence_rating` vs `defense_rating` (both exist); `match_id`/`external_match_id`/`match_external_id`; `calculated_at` vs `computed_at` vs `evaluated_at` vs `updated_at`; `readiness_score` on three tables meaning three different formulas; `home_goals` on `match_performance_comparison` meaning *predicted* goals. | Schema-wide |
| TD-6 | **21 ARRAY columns and 9 jsonb columns hold relational content** — narrative bullets, player ID lists, formation lists, risk factors, signals. Unqueryable, unindexable, and `position_coverage.primary_players` holds player references outside the FK system entirely. | Doc 02 |
| TD-7 | **Missing constraints.** No FK on `season_external_id` (5 tables); competition identified by text `league_name` in 3 calibration tables; `matches.competition`/`matches.season` text duplicating FK columns; `teams.country`/`stadiums.country`/`players.nationality` free text beside a populated `countries` table; polymorphic `entity_id` on `watchlists`/`notifications`. | Doc 01 §3.4 |
| TD-8 | **Constraint drift between repository and live database.** Five processors upsert on conflict targets that exist in no migration (`squad_depth`, `team_versatility`, `formation_analysis`, `position_coverage`, `position_depth_comparison`). A code comment asserts migration 032 added them; it did not. | Doc 01 §5.5 |
| TD-9 | **Wide tables.** `player_season_statistics` at 118 columns mixes goalkeeper and outfield metrics; ~50 columns are permanently null for any given player. `match_intelligence` 42, `match_performance_comparison` 38. | Doc 02 |
| TD-10 | **Generated prose in metrics tables.** `recommended_approach`, `executive_brief`, `matchup_description`, `battle_outcome_prediction`, plus 6 `*_notes` columns. | Doc 02 |
| TD-11 | **Synthetic data indistinguishable from measured data.** `match_weather` is generated by a seeded PRNG over climate zones and consumed by a paid module, with no provenance column. `player_transfers.source` is the only provenance marker anywhere in the schema. | Doc 01 §5.6 |
| TD-12 | **Duplicated state between application code and database.** Plans and prices in `tier.ts` vs `subscription_plans`; feature keys in `access.ts` vs `feature_permissions`; module definitions and baselines only in `modules.ts`; league coverage only in `trackedLeagues.ts`. | Doc 03 §3.2 |
| TD-13 | **Two coexisting entitlement paths.** `tier.ts:currentTier()` reads `NEXT_PUBLIC_DEFAULT_TIER` from an env var; `access.ts` reads the database. Both are live in the codebase. | `tier.ts:77` |
| TD-14 | **`match_signals` allows one signal per market per fixture** (`UNIQUE (match_id, market)`) despite carrying `signal_group` and `rule_key` columns implying many. A second firing rule overwrites the first. | Doc 02 |
| TD-15 | **Injury state duplicated** between 10 columns on `players` and the `player_injuries` table, both written by the same job, with no constraint tying them. | Doc 02 |

### A2. Scaling problems

Targets: 10+ years of history · 100+ leagues · millions of player statistics · many users · subscription tiers.

| # | Problem | Impact at target scale |
|---|---|---|
| SC-1 | **No partition key.** Most match-scoped tables carry only `match_id` + `calculated_at` (processing time, not match date). Time-range queries require a join to `matches`. | 50–100M rows in unpartitioned heaps |
| SC-2 | **No hot/cold separation.** A fixture kicking off tomorrow and one played in 2016 share the same table, indexes, and vacuum behaviour. | Index bloat; cache thrash |
| SC-3 | **Full-table reprocessing every run.** L1–L3 and L5–L6 are explicitly "always full" even in date-scoped variants. Currently ~323 teams; at 100 leagues it is 2,000+ teams and 50,000+ players. | The documented 30–120s runtime does not survive a 6× expansion |
| SC-4 | **Team singletons cannot hold 10 years or multiple competitions.** One row per team, no season dimension, overwritten in place. | Historical coverage is structurally impossible in the current shape |
| SC-5 | **Row-count hot spots.** `player_matchup` up to 121 rows/match (~46M); `match_predicted_lineups` ~26/match (~10M); `player_match_impact` ~22/match (~8.4M); `player_match_load` ~10M; `team_squads_snapshot` ~7.3M with no retention policy. | Storage and vacuum pressure |
| SC-6 | **Read amplification.** Match page = ~30 parallel queries; board = 12. No read model, view, or RPC. | Connection pool, not CPU, becomes the limit |
| SC-7 | **Ingestion is quota-bound.** Two API keys = 200 requests/day. Nothing records quota consumption. | At 100 leagues, freshness is gated by an unmeasured external budget |
| SC-8 | **Text-keyed calibration collides across countries.** `league_gap_summary.league_name` is UNIQUE; several competition names recur across leagues. | Calibration data merges silently between unrelated competitions |
| SC-9 | **Index coverage skewed to the raw layer.** ~50 migration-created indexes, overwhelmingly on `matches`/`teams`/`players`; the 31 match-scoped intelligence tables mostly have PK + one unique. Production index state is UNVERIFIED. | Unknown, and unknowable from the supplied dump |
| SC-10 | **Module evaluation is O(fixtures × modules) per request** with no caching or persistence. | CPU cost scales with traffic, not with data |

## Part B — What V2 must support

### B1. Temporal correctness (highest priority)

1. Every intelligence value must be **addressable at a point in time** — "what did we believe about this team on 2024-03-01" must be answerable without reconstruction.
2. A **finished match's intelligence must be immutable**, uniformly across every intelligence table, not on 1 of 31.
3. A **new formula version must be able to coexist** with the old one over the same history, so a corrected model can be evaluated retroactively without destroying the original record or violating immutability.
4. Rolling-window metrics (`last_7_days`, `next_14_days`) must carry the **date they were computed as of**, so a stale row is distinguishable from a fresh one.

### B2. Versioning and provenance

5. Every derived value must record **which model/formula version produced it**. Today: one column in 92 tables.
6. Every stored fact must record **where it came from** — provider-measured, provider-inferred, internally calculated, or estimated/synthetic. `match_weather` and `player_transfers` prove both the need and (in the latter case) the pattern.
7. Every published rate must carry its **sample size and confidence interval**, systematically rather than in five tables that happen to do it. The `Baseline` contract in `modules.ts` ("a historical rate without an n is a marketing number, not evidence") is the product's stated standard and the schema should enforce it.

### B3. A first-class module layer

8. Modules must exist **as data**: a registry (key, name, question, scope, tier, version, active) rather than a TypeScript union in the frontend.
9. Module **outputs must be stored**, not recomputed per render — one generic module-result structure keyed by `(module, entity, entity_id, computed_at, version)`, generalizing the shapes already proven by `match_tactical_advantages` and `team_strengths`/`team_weaknesses`.
10. Module **baselines must be read from the calibration tables**, not hardcoded literals, so a re-backtest updates what the product shows.
11. Adding a module must require **one registry row + one processor**, not 11 coordinated changes across two repositories.
12. **One taxonomy** must connect module keys, signal rule keys, and backtest keys, so a module can display its own measured evidence.

### B4. Deduplication and a single source of truth

13. **One authoritative value per concept per entity per point in time.** Where a copy exists for read performance, it must be an explicitly derived/materialized object, not a hand-maintained duplicate column.
14. **One match prediction**, or an explicit model-identity dimension making multiple predictions first-class and comparable rather than accidental.
15. Inputs and outputs must be **separable** — a stored prediction must reference the input snapshot it consumed rather than embedding copies of it.

### B5. Referential and semantic integrity

16. Season must be **one concept with one key** — no `season_external_id` without an FK.
17. Competition must be identified by **ID everywhere**, including the calibration tables that key on `league_name` today.
18. Provider passthrough vocabularies (`matches.status`, `position_code`, `market`, `advantage_type`, `weather_condition`, `transfer_type`) must be either **constrained or explicitly mapped to internal enums**. `matches.status` is load-bearing for the immutability trigger and four processors' scoping and is currently an unenumerated external string.
19. Structured content must be **relational, not ARRAY/jsonb** — especially anything holding entity references.
20. All dependency edges currently encoded in `cli.ts` ordering should be **discoverable from the schema** (declared inputs per calculated artefact), so a missing input fails loudly rather than writing nulls.

### B6. Scale

21. A **partition/archival strategy** keyed on match date, with the date available on the fact itself.
22. **Incremental recomputation** — process only what changed, not every team and player on every run.
23. **Read models** for the hot pages (match, board, team, league), so a page is a small number of queries.
24. A **retention policy** for daily snapshot tables.
25. Multi-competition and multi-season coverage per team as a **first-class dimension**, not an assumption that a team has one state.

### B7. Operational observability

26. A durable record of **every pipeline run**: job, scope, start/end, rows written per table, errors, and outcome. Today this exists only in stdout logs.
27. **API quota consumption tracking**, since ingestion is quota-bound.
28. **Data freshness per table**, so the UI can distinguish "no edge detected" from "the processor did not run".
29. **Data-quality assertions** (coverage, null rates, range checks) recorded as results, not as a script that prints and exits — `verify:historical-integrity` currently writes nothing.

### B8. Product layer

30. Plans, features, and entitlement rules must live in the database only — **no duplicate plan/feature definitions in application code**.
31. **One entitlement path**, not an env-var tier and a database tier coexisting.
32. Feature gating must express **per-plan matrices**, not only a single minimum plan per feature.
33. RLS posture on the football/intelligence layer must be **explicit and uniform** — today exactly one football table (`match_half_time_intelligence`) has a policy.

## Part C — What must remain compatible

### C1. Must not be removed or broken

| Asset | Why |
|---|---|
| `readiness_history` + its immutability lock | The only defensible historical record of what the product predicted and whether it was right. Every published hit rate depends on it. |
| `match_intelligence` immutability trigger (migration 042) | Written in response to a specific production incident (a processor rewriting finished matches' intelligence). Its posture — protect whenever `status IS DISTINCT FROM 'scheduled'` — must survive, and should be generalized rather than relaxed. |
| `signal_backtests` with Wilson intervals + `is_calibrated` | The evidence layer. `ci_low`/`ci_high` and the sample gate are load-bearing for the product's honesty claims. |
| `league_gap_analytics` / `league_gap_summary` incl. `meets_sample_gate` | Per-league calibration with an explicit sample gate. |
| `team_match_snapshots` / `match_opponent_context` | The only point-in-time reconstruction the backtests can use. Cheap to rebuild but expensive to re-derive the logic for. |
| The single-writer discipline (service key writes football data; anon key never does) | The clearest architectural boundary in the system. |
| `process:all-db` idempotence and L1→L6 dependency ordering | The regeneration guarantee. All ~50 dependency edges must be carried over. |
| `confidenceBand.ts` shared definitions (`BAND_FLOOR`, `derivePick`, `DRAW_GAP_BAND`) | The published thing and the backtested thing are byte-identical by construction. V2 must not reintroduce divergence. |
| RLS policies + `is_admin()`/`staff_role()`/`role_rank()`/`can_access_feature()`/`subscriptions_enabled()` | The entire security model of the user layer. |
| `handle_new_user()` trigger + `guard_profile_self_update()` | Auth bootstrap and privilege-escalation guard. |
| `prune_watchlist_entity()` triggers | The only referential defence for polymorphic references. |
| `trackedLeagues.ts` coverage semantics (slug exact-match for squads, name-fragment for feeds, `dbNames` overrides for sponsor renames) | Encodes hard-won knowledge about provider naming. Moving this to data must preserve all three matching strategies. |

### C2. Must be preserved as data

- All raw football history: `matches`, `match_results`, `teams`, `players`, `tournaments`, `seasons`, `stadiums`, `countries`, `player_season_statistics`, `team_season_statistics`, `tournament_standings`, `player_transfers`, `player_injuries`, `team_squads_snapshot`. **Re-ingestion is not a fallback** — the external APIs are quota-limited and historical windows may no longer be retrievable.
- `team_form_history` — cheap to rederive, but it is the input to almost everything and any rebuild must be verified against the original.
- All four calibration tables, plus `team_intelligence_history` (the only multi-day trace of team state that exists).

### C3. Must remain compatible for the frontend

- `lib/queries.ts` is the single query layer. Every table it reads and every column it selects is a compatibility surface — including the 13 materialized views.
- The `MatchRow` / `TeamLite` / `TournamentLite` shapes in `lib/types.ts` are consumed by ~40 components.
- Slug-based routing depends on `teams.slug`, `tournaments.slug`, and `matches.external_match_id`.
- Nested PostgREST joins (`tournament:tournaments(country:countries(...))`, `home_player:players!fk_name(name)`) depend on **specific FK constraint names**. Renaming a FK breaks the query silently at runtime, not at build time.
- The mock-data fallback path means a broken query degrades to demo data rather than erroring — migrations must be verified against real data, not by "the page still renders".

## Part D — Migration risk assessment

### D1. Cannot be removed

- Everything in C1 and C2.
- The four tables referenced by no code (`customers`, `notifications`, `notification_preferences`, `match_intelligence_watch`). Per the Phase 1 rules these are **not** assumed unnecessary: `customers` is staged Stripe infrastructure, `match_intelligence_watch` is the only place `module_consensus`/`evidence_count` appear, and the notification tables encode a designed product surface (`friday_briefing`, `consensus_changes`, `module_changes`). **Product decision required — see doc 05 item 12.**
- The 28 tables written by the backend but not read by the frontend. Most are pipeline intermediates with live downstream consumers; several (`player_injuries`, `team_intelligence_history`, `player_transfers`, `team_travel_load`) hold data the UI is documented as wanting.

### D2. Requires migration (data movement, not just DDL)

| Item | Risk | Note |
|---|---|---|
| 17 team singletons → any temporal shape | **High** | No history exists to migrate; migration creates the shape, the history starts at cutover. Accept and document the discontinuity. |
| 31 match-scoped tables → generic module results | **High** | Highest-volume transformation; must preserve the immutability semantics of `match_intelligence` during the move. |
| `season_external_id` → real FK | **High** | Requires that every referenced season exists in `seasons`. **Verify first** (doc 05 item 5) — orphans will block the constraint. |
| `league_name` → `tournament_id` in 3 calibration tables | **High** | Name-to-ID resolution over historical rows where the name may since have changed. Unresolvable rows must be quarantined, not dropped — this is the calibration record. |
| `player_season_statistics` split (outfield/GK/common) | Medium | 118 columns, ~500k rows; mechanical but large. |
| `players` injury columns → `player_injuries` only | Medium | Requires reconciling two representations that may disagree today. |
| ARRAY/jsonb → relational children (21 + 9 columns) | Medium | `position_coverage.primary_players` holds unvalidated player IDs; expect orphans. |
| `matches.competition`/`season` text → drop in favour of FKs | Medium | Verify the text and the FK agree on every row before dropping either. |
| Module registry + baselines out of `modules.ts` into data | Medium | Baselines include a documented `"unreplayed"` cohort with lookahead bias — migrate the provenance marker, not just the numbers. |
| `trackedLeagues.ts` → data | Medium | Must carry all three matching strategies and the `dbNames` sponsor-rename overrides. |
| Plan/feature definitions out of `tier.ts` | Low | Small, but touches billing-adjacent behaviour. |

### D3. Requires validation before any design work

1. **Reconcile the repository against the live database.** The dump omits composite uniques, indexes, views, functions, triggers, and RLS; five upsert targets have no in-repo constraint; `team_form_history`'s CHECK is rendered `NOT VALI)` in the supplied file. **Until a full `pg_dump --schema-only` is available, the repository is not a reliable description of production.**
2. **Obtain the 13 materialized view definitions.** Two are on the match-page and board hot paths.
3. **Verify orphans** before adding FKs: `season_external_id` values not in `seasons`; `league_name` values not resolvable to a tournament; player IDs inside `position_coverage.primary_players`/`secondary_players`; `watchlists.entity_id`.
4. **Verify snapshot uniqueness** on `team_squads_snapshot`, `team_fixture_load`, `team_travel_load`, `tournament_standings`, `player_match_load` — if duplicates exist today, a naive unique constraint fails and a naive dedupe changes history.
5. **Verify agreement between duplicated columns** (`matches.competition` vs `tournament_id`; `match_results.status` vs `matches.status`; `players` injury columns vs `player_injuries`; `team_intelligence.congestion_score` vs `team_fixture_load`). Disagreement rates determine which copy is authoritative.
6. **Confirm which of the two competing match predictions is authoritative** — a product decision with no technical answer.
7. **Quantify `match_weather`'s synthetic footprint** and decide whether Module 13 continues to ship on estimated data.

### D4. Features that depend on the current structure

| Feature | Depends on |
|---|---|
| Match page | ~30 tables + 2 materialized views; FK **constraint names** for nested joins |
| Board / matches feed | `matches` + `mv_module_travel` + `mv_match_scoring_probabilities` + 10 tables |
| 13 modules | Base-table column names read by `modules.ts` evaluators + hardcoded baselines |
| Tier gating | `platform_settings.subscriptions_enabled`, `feature_permissions`, `subscription_plans.rank`, `user_subscriptions.status` |
| Admin console | `user_profiles`, `user_subscriptions`, `admin_actions`, `user_notes`, `platform_settings`, `signal_backtests`, `league_gap_*` |
| Backtest / calibration | `readiness_history` (+ lock), `team_match_snapshots`, `match_opponent_context`, `signal_backtests`, `league_gap_*` |
| Predicted XI | `match_predicted_lineups` (`x`, `y`, `role`, `lineup_order`, captain flags) + `match_predicted_formations` |
| Watchlist | `watchlists` + 3 prune triggers |
| Auth / signup | `handle_new_user()` on `auth.users`, `user_profiles` + role guard trigger |

### D5. Recommended sequencing (for Phase 2 discussion, not a plan)

1. Close the schema-fidelity gap (D3.1, D3.2) — nothing else is safe until the repo describes production.
2. Run the validation queries (D3.3–D3.5) and publish the results as the migration's factual baseline.
3. Resolve the product decisions (D3.6, D3.7, D1's four unused tables).
4. Only then design V2, additively — new structures alongside old, dual-write, verify, cut over, and retire nothing until the frontend has moved.
