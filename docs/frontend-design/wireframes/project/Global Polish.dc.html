Phase K · Global polish · rules

1 · Principles. One surface hierarchy (ink → panel → raised), one table grammar, one status language, one state grammar. Failures stay in their section; missing is never zero; nothing is inferred in the UI.

2 · Responsive. The breakpoints are Tailwind's 640 / 768 / 1024. Desktop is a 1152 rail with 8/4 or 7/5 splits. Tablet (768–1023): rails stack under main; 6+6 lineups stay side by side. Mobile (<768): one column, 12px gutters, tabs and chips scroll horizontally at 44px, type stays fixed. Names truncate with ellipsis inside a min-width:0 cell, and the full name stays in the aria-label or on the entity page. Only dense tables scroll horizontally.

3 · Loading. Header and tabs render first. The body shows static panel skeletons in the final layout (no shimmer), with aria-busy and one "Loading" status per region. The pulse dot is reserved for in-flight actions and LIVE. All motion stops under prefers-reduced-motion (now added to every component).

4–5 · Empty and error (1a). NO DATA (solid tag): the request succeeded and returned nothing, e.g. "No fixtures for this date." NO MATCHES: a filter or search excluded everything; offers Clear. ◌ NOT AVAILABLE (dashed): the product doesn't provide this. ! COULDN'T LOAD (role=alert): the request failed; offers Try again, never an error code. The earlier "ABSENT" tag was renamed NO DATA everywhere. Match Timeline now uses NOT AVAILABLE. Legal "Retry" is now "Try again".

6 · Partial data. Every panel owns its own loading, empty, unavailable and error state. The entity header always renders if identity loaded. Unrecorded values show — in --faint; small samples are flagged in text.

7 · Gating (1h). ◇ ACCESS RESTRICTED replaces only the section body. The heading stays, so the capability is visible, and one "See plans" link goes to Pricing. No plan is named and nothing is blurred or teased. Fixtures, results, tables and identity are never gated in design. Which sections are gated, and for whom, comes from an entitlement contract.

8 · Accessibility. A global :focus-visible amber 2px ring was added to every component. Landmarks: header / nav / main / footer. h1 is the entity or page, h2 each panel. Tabs use role=tab + aria-selected (Account uses nav + aria-current). Tables use role=table with headers. Forms have visible labels and aria-describedby errors. Targets are 44px on mobile. The smallest text is 10px mono labels; the 8.5px tags are designer annotations only and switch off with annot=false.

9 · Status (1b). Scheduled shows the kickoff time · ● LIVE · ■ FT / AET / PEN (only when the result carries them) · ▲ POSTPONED / ABANDONED · ✕ CANCELLED · ? UNKNOWN. A confirmed 0–0 shows "0 – 0 FT"; a missing result shows "— FT"; not played shows "–".

10 · Tables on mobile. Standings keep # · Team · P · GD · Pts, with the rest in the row expansion. Fixtures keep time or status · teams · score. Squad and player logs drop secondary numerics, which stay reachable in Performance. Statistics stay three columns with short bars. Tables never turn into cards, except squad rows at <768.

11–12 · Navigation and components. The same AppHeader everywhere (Account via the account menu). Breadcrumbs are mono uppercase links separated by /. Tabs sit on the underline with an amber 2px rule. Entity links are --cool. Shared components kept to the ones with real reuse: AppHeader, StatePanel, the status chip, the result badge, the fixture row, and the kv list.

14 · Remaining inconsistencies (left as-is, called out)

  • Account's section nav is vertical where the entity workspaces use horizontal tabs. This is intentional (settings versus data) but is the one exception to the tab grammar.
  • The Legal and auth pages use the focused shell, not AppHeader. This is intentional for task focus.
  • StatePanel is new; the page files still inline equivalent markup. Adopting it in code is an implementation task, and the visuals already match.
  • Tablet headers on Competition, Team and Match keep desktop meta alignment down to 768; below that it's left-aligned.

15 · Needs backend contracts before implementation

  • Entitlements (what is gated, and for whom) and the tier → access mapping
  • Account, subscription, billing and session; the password-reset flow
  • A unified search endpoint
  • A venue → matches endpoint; a match events (timeline) feed
  • Pricing values; the checkout/payment provider
  • The meaning of the statistics compareCode; the player rating scale
  • Whether the live-context module verdicts on /matches/:id should ever surface next to the kickoff reading
